# 变现与授权码运营手册

这份文档写给「谁在偷跑」的商业化环节：定价怎么定、授权码怎么签发、钱怎么收、货怎么发、退款怎么办、一个码被公开传播了怎么办。

App 内置的购买说明写的是：「本项目在 GitHub 上开源发布，装机包在 Releases 里，授权码单独出售（这样源码和付费是分开的，源码随便看）。买断 ¥18 / 订阅 ¥6 月 / ¥48 年，付款后把订单号发给开发者，会给你一串授权码。」

这份文档就是把上面那句话展开成可执行的流程。

---

## 一、定价方案

| 套餐 | 价格 | 授权码里的 `plan` | `exp`（到期时间） |
|---|---|---|---|
| 买断 | **¥18** | `buyout` | `0`（表示永久不过期） |
| 订阅（月） | **¥6 / 月** | `subscription` | 签发时刻 + 30 天 |
| 订阅（年） | **¥48 / 年** | `subscription` | 签发时刻 + 365 天 |

### 为什么是这几个价

- **¥18 买断**是主推项。一次性付清、没有到期日、心理负担最小。按「每天不到五毛钱」算，买断用户最容易下决心。
- **¥6 / 月**是给「先试试水」的人准备的入口。它和买断的差价（12 元）意味着，只要用户打算用超过 2 个月，买断就明显划算 —— 这个差价本身就是自然的选择引导，不需要额外营销。
- **¥48 / 年**等于 8 个月的月付价格（48 ÷ 6 = 8），比按月付省三分之一。年付能显著降低流失率，同时不把年客单价压到太低。
- **免费版必须给够。** 用户得能真正看出「这台手机确实有 App 在偷跑」，否则 ¥18 卖不动。所以免费版给的是**完整可用的一次审计**，只是限制了时间范围和榜单长度，不做功能阉割。

### 定价之外的一个现实约束

**授权码一旦签发出去，就无法远程作废。** 因为整个体系是离线的 —— 没有服务器，就没有「查一下这个码还在不在」的入口。这条约束反过来影响了定价和收款方式的选择，详见第八节和第九节。

## 二、免费版边界

### 产品规则

| 能力 | 免费版 | 买断 / 订阅 |
|---|---|---|
| 审计时间范围 | 只看最近 **24 小时** | 全部历史范围（1 小时 / 3 天 / 7 天 / 30 天） |
| 榜单长度 | 只显示前 **3 条** | 全部 |
| CSV 导出 | 不可用 | 可用 |
| 全部证据明细（时间点、描述） | 受限 | 完整 |
| 定期告警通知 | 受限 | 完整 |

### 实现现状（2026-11-20，写这份文档时的真实状态）

诚实起见，把「规则」和「代码现在做到了什么」分开列：

| 限制 | 代码现状 |
|---|---|
| 榜单前 3 条 | ✅ 已生效（`home_screen.dart` 里 `ranked.take(LicenseService.freeAppLimit)`） |
| 只看最近 24 小时 | ⚠️ **未生效**。`LicenseService.isUnlocked()` 写了 24 小时和条数两个条件，但这个方法目前**全项目没有任何调用点**；时间范围选择器对未付费用户同样开放 |
| CSV 导出 | ⚠️ **未生效**。首页和设置页的导出按钮目前对免费用户也可用 |

也就是说，现在靠 UI 把前 3 条之外的藏起来，其余两条限制实际上没有代码拦截。**要么补上限制，要么别在文案里承诺。** 当前 UI 文案（「免费版只看最近 24 小时、榜单前 3 条」）已经写了后两条，属于**承诺大于实现**，需要尽快补齐。

补齐的最小改法：在 `AuditService.runAudit()` 里按授权状态钳制 `sinceHours`（免费版一律 24），在 `ExportService.exportCsv()` 的调用处加一道 `unlocked` 判断。

### 已激活用户的判定

```
unlocked = 授权码存在 && 验签通过 && (是买断 || 未过期)
```

过期判定完全靠本机时钟（`expiresAt.isBefore(DateTime.now())`）。**这意味着用户把手机时间调回去就能延长订阅。** 目前不做处理：单个用户作弊的收益很小，而引入联网校时会直接破坏「不联网」这条最硬的隐私承诺。如果将来订阅收入占比变高需要处理，方案是绑定设备指纹（见第十节），而不是接服务器。

## 三、授权码机制

### 3.1 格式

```
WR1.<payload 的 base64url>.<签名的 base64url>
```

payload 是一段 JSON：

```json
{
  "v": 1,
  "plan": "buyout",
  "exp": 0,
  "iat": 1763610000000,
  "note": "2026-11 批次A 第 3 张",
  "bind": ""
}
```

| 字段 | 含义 |
|---|---|
| `v` | 格式版本，目前固定为 `1`。App 验签时要求 `v == 1`，不认识别的版本 |
| `plan` | `buyout` 或 `subscription` |
| `exp` | 到期时间戳（毫秒）。`0` = 永久 |
| `iat` | 签发时间戳（毫秒） |
| `note` | 备注。用于标记批次、订单号、签发人，**不影响验签和功能** |
| `bind` | 绑定的设备指纹。空字符串 = 不绑设备 |

### 3.2 验签流程（App 侧，全程离线）

```
用户在激活页粘贴授权码
        ↓
拆成三段，必须正好三段，且前缀是 WR1
        ↓
base64url 解出 payload 和 signature
        ↓
用内置的 Ed25519 公钥验签
        ↓
验签失败 / v 不认识 → 拒绝，提示「授权码无效或已被篡改」
        ↓
验签通过 → 读 plan / exp
        ↓
已过期 → 拒绝，提示到期日期
        ↓
bind 不为空且与本机指纹不符 → 拒绝，提示「绑定在另一台设备上」
        ↓
写入 SharedPreferences（license_code、license_device）
```

**为什么用离线验签而不是服务器校验：**

1. **没有服务器成本。** 不用维护服务、数据库、监控，也不用担心服务挂了卖不出货。
2. **不破坏隐私承诺。** App 全程没有网络权限，激活授权码不需要联网，不会产生「为了卖钱而收集用户数据」的观感 —— 这对一个隐私工具是致命的。
3. **验证逻辑可审计。** 授权码是自签名的，拿到码的人可以自己用工具验一遍，确认没有被中间人改过。
4. **离线可用。** 用户在没网的环境里也能激活。

**代价：** 无法远程吊销、无法远程续期、无法统计活跃用户。这些代价在当前规模下可以接受。

### 3.3 密钥对

- **算法**：Ed25519。
- **私钥**：只存在 `../.whoruns-secrets/license_key.json`（相对仓库根目录，即仓库外的同级目录）。**绝不能提交进 git。**
- **公钥**：硬编码在 `lib/services/license_service.dart` 的 `LicenseService.publicKeyHex`，编译进 App。

当前这一对密钥已经配好了：App 内置的公钥与 `.whoruns-secrets/license_key.json` 里的公钥一致，可以直接签发、验签通过。

## 四、签发工具 `tool/license_tool.dart`

工具是纯 Dart 脚本，跑在 `dart run` 下。**只需要在你自己有私钥的机器上跑**，用户不需要、也不应该能跑。

### 4.1 生成密钥对（只做一次）

```bash
dart run tool/license_tool.dart keygen
```

输出示例：

```
密钥已写入：../.whoruns-secrets/license_key.json

公钥（贴到 lib/services/license_service.dart 的 publicKeyHex）：
6978d96b74969433625776b31a1424c30a5b311d0a3c3dcd06d165940fc4d0e4

私钥只存在这个文件里，别提交进 git。
```

**注意事项：**

- 如果密钥文件已存在，工具**不会覆盖**，只会打印现有公钥并退出。这是防手滑的保护，别去手动删了重建，除非你真的打算换密钥。
- 生成的公钥要手动贴进 `lib/services/license_service.dart` 的 `publicKeyHex`，然后**重新构建 App**。不贴的话 App 验签必失败。
- 想放到别的目录，用 `--dir <路径>`：
  ```bash
  dart run tool/license_tool.dart keygen --dir D:/secure/whoruns-keys
  ```
  这个目录**不要放在仓库里**。仓库根目录的 `.gitignore` 需要确保覆盖了它 —— 更稳妥的做法是根本放在仓库外。

### 4.2 签发授权码

```bash
dart run tool/license_tool.dart issue --plan buyout --count 5
```

一次签 5 张买断码，每行一张，直接打印到 stdout。

```bash
dart run tool/license_tool.dart issue --plan subscription --days 365 --count 3
```

签 3 张一年期订阅码。

```bash
dart run tool/license_tool.dart issue --plan buyout --note "2026-11-批次A" --count 10 --out codes-2026-11.txt
```

签 10 张买断码，备注写批次号，同时写进 `codes-2026-11.txt`。

```bash
dart run tool/license_tool.dart issue --plan subscription --days 30 --note "订单 GM20261120-0042"
```

按订单签一张月付码，备注里带上订单号 —— 后面查账全靠这个。

### 4.3 参数表

| 参数 | 取值 | 说明 |
|---|---|---|
| `--plan` | `buyout` \| `subscription` | 套餐。默认 `buyout` |
| `--days` | 整数 | 订阅有效期天数。`buyout` 时忽略（`exp` 固定为 0） |
| `--count` | 整数 | 一次签几张。默认 1 |
| `--note` | 文本 | 备注字段。建议写批次号或订单号，方便日后对账 |
| `--bind` | 设备指纹 | 绑定到指定设备。空 = 不绑定 |
| `--out` | 文件路径 | 把签出的码写进文件（每行一个），同时仍打印到 stdout |
| `--dir` | 目录路径 | 密钥文件所在目录。默认 `../.whoruns-secrets` |

### 4.4 验签

```bash
dart run tool/license_tool.dart verify WR1.xxxxxxxxx.yyyyyyyyy
```

输出：

```
签名有效
{"v":1,"plan":"buyout","exp":0,"iat":1763610000000,"note":"2026-11-批次A 第 1 张","bind":""}
```

`verify` 读的是**密钥文件里的公钥**，不是 App 里的。所以它能验出「这个码是不是我签的」，但验不出「这个码在当前发布的 App 里能不能用」—— 那取决于 App 里内置的公钥是不是同一把。换密钥后这两者可能不一致（见第六节）。

### 4.5 一个容易踩的坑

`--count` 循环里的 `note` 默认值是 `第 N 张`（第几张）。**如果你要用 `--note` 追踪批次，务必自己写批次号**，否则批量签出来的码备注都一样，事后对不上单。

## 五、私钥保管

| 事项 | 做法 |
|---|---|
| 存放位置 | 仓库外的 `../.whoruns-secrets/license_key.json` |
| 备份 | **至少两处**：一份本地磁盘，一份加密的云盘或密码管理器附件。丢了就永远签不出能被现有 App 验证的码了 |
| git | 确认它没被 `git add` 过。用 `git check-ignore -v ../.whoruns-secrets/license_key.json` 验证 |
| 传到别的机器 | 用 scp / 密码管理器传，别走微信、别走邮件附件、别放进网盘同步目录 |
| CI | **绝不能把私钥放进 GitHub Actions 的 secrets 然后在 workflow 里签发**。那样任何能改 workflow 的人都能签发任意码 |
| 权限 | 文件权限设成只有自己能读（Linux/macOS 下 `chmod 600`） |

**私钥泄露了怎么办：** 按第六节「换密钥」处理，没有别的办法。

## 六、换密钥的代价

**换密钥 = 让所有已经发出去的授权码全部作废。**

具体流程和代价：

1. `keygen` 生成新的一对。
2. 把新公钥贴进 `lib/services/license_service.dart`。
3. 重新构建、重新发布 App。
4. 给每一个已付费用户发新码，并要求他们重新输入。
5. 每一个买断用户（累计所有买断用户）都会收到一封「请重新激活」的邮件，还要处理由此产生的客服量。

**为什么 App 里只有一把公钥。** 当前实现只支持单个 `publicKeyHex`。要实现「平滑换密钥」，需要改成公钥列表（同时验签多把，新旧码都能用，等旧码自然过期或用户主动更新后再移除旧公钥）。**这是个应该做但还没做的改动**，现在换密钥仍然是「一刀切」。

**因此：不要随便换密钥。** 只在私钥真的泄露了、或者你决定做「平滑换密钥」改造之后才换。

## 七、收款渠道

三个可选方案的实际对比。**费率以各平台当时的官方说明为准**，本文不写具体数字，因为这些数字变动比文档快。

### 7.1 微信 / 支付宝收款（个人码或商户码）

| 项 | 说明 |
|---|---|
| 适合谁 | **主要面向国内用户**的场景 |
| 优点 | 付款门槛最低；用户用微信/支付宝一扫就付，转化率最高；没有平台抽成，也没有平台的数据留存顾虑 |
| 缺点 | 几乎无法自动化；每笔订单都要手工确认、手工发货；个人收款码存在被风控/限额的现实风险；不适合规模化 |
| 和本项目的适配 | 好消息是本项目**本来就是手工发货模式**（App 内文案就是「付款后把订单号发给开发者」）。所以人工发货不是负担，反而是最省事的做法 |

### 7.2 Gumroad

| 项 | 说明 |
|---|---|
| 适合谁 | 有海外用户、或想省掉手工发货的阶段 |
| 优点 | 数字产品开箱即用；自动交付文件/授权码；自带订单管理和税费处理；支持创作者收款 |
| 缺点 | 需要国际支付方式，**国内用户没法直接用支付宝/微信付款**；平台按其公布的费率抽成；国内访问体验一般 |
| 和本项目的适配 | ⚠️ **有一个结构性问题**：Gumroad 自动发给你的是它自己的 license key，而本 App 只认 Ed25519 签名的码，**平台发的 key 在本 App 里激活不了** |

### 7.3 Lemon Squeezy

| 项 | 说明 |
|---|---|
| 适合谁 | 已经在用或愿意用海外支付/税务合规工具的开发者 |
| 优点 | 面向数字产品；有 license key 管理和 API（可以做成自动化流程）；支持商家模式税务处理 |
| 缺点 | 同样需要国际支付方式；国内用户付款不便；平台抽成；上手配置比 Gumroad 复杂一点 |
| 和本项目的适配 | ⚠️ 和 Gumroad 同一个结构性问题：平台生成的 license key 无法被离线验签方案接受 |

### 7.4 怎么解这个结构性问题

三个选项，按推荐顺序：

**方案 A（推荐，早期用这个）：平台只负责收款，交付仍然手工。**

在 Gumroad / Lemon Squeezy 上把商品设成「付款后由卖家手动交付」，用户付款后把订单号发给你，你用 `tool/license_tool.dart issue` 签一张码发过去。这跟微信收款的发货流程完全一样，只是多了一个平台做收款和记账。

**方案 B：平台自动发一个占位内容，用户拿订单号来找你。**

平台自动交付一个文本文件（比如写着你的订单号或一个兑换 token），用户把它发给你，你签真码。省掉了「记住订单号」这一步，但多绕一道。

**方案 C：让 App 也接受平台 key。**

这要求 App 联网向平台验证 license key，**直接违背本项目「不联网、不收集数据」的核心承诺**。不推荐，也不该为了省几分钟手工发货这么做。

### 7.5 最终建议

**当前阶段：微信/支付宝收款 + 手工发货。**

理由很直接：本项目的收入来自国内普通用户，他们用微信付款最顺手；而我们本来就要手工发货，Gumroad/Lemon Squeezy 唯一多出来的价值是「自动发货」，而这个价值恰恰因为授权码方案的差异而用不上。**先不要为了用平台而用平台。**

等到有稳定的海外用户、或者单量涨到手工发货忙不过来的时候，再上 Gumroad，并采用方案 A。

## 八、发货流程

```
① 用户付款
      ↓
② 收到订单（订单号 / 付款截图 / 用户邮箱或微信）
      ↓
③ 核对：付款金额对应哪个套餐？有没有重复付款？退款记录？
      ↓
④ 签发
   dart run tool/license_tool.dart issue --plan buyout --note "订单号 XXX"
   （订阅：--plan subscription --days 30 或 --days 365）
      ↓
⑤ 交付：把 WR1. 开头的码发给用户（微信 / 邮件 / 平台私信都行）
      ↓
⑥ 用户在 App「解锁完整版」页粘贴 → 激活 → 永久解锁或按期解锁
```

### 交付时应该附的话

不要只甩一串码。给用户的说明里应该包含：

```
授权码：WR1.xxxxxxxxx.yyyyyyyyy

· 打开 App → 设置 → 解锁完整版 → 粘贴 → 激活
· 一次买断，永久可用，App 以后升级不另外收费
· 授权码只在这台手机上生效，别转发给别人
· 换手机了或者要退订，联系 wangjinchao@castianta.com
```

### 记录

每笔订单至少记三样：**订单号、签发时间、授权码的 note 字段**。`note` 里带上订单号是关键 —— 授权码本身是一串 base64url，没人能从里面看出是哪一单，靠 note 才能对账。

建议维护一张表：

| 订单号 | 套餐 | 金额 | 签发时间 | note | 状态 | 备注 |
|---|---|---|---|---|---|---|
| GM20261120-001 | 买断 | ¥18 | 2026-11-20 | GM20261120-001 | 已交付 | |
| GM20261120-002 | 订阅年 | ¥48 | 2026-11-20 | GM20261120-002 | 已交付 | |

### 订阅续费

订阅到期后功能自动失效。续费时**签一张新的码**（`iat` 是新的，`exp` 顺延），让用户重新输入。因为没有服务器，App 不会自动续期 —— 这是离线方案的必然结果，也是用户激活时能看到「订阅还有 N 天到期」的必要原因。

## 九、退款与换机

### 9.1 一个必须先讲清楚的事实

**离线授权码无法远程吊销。** 你没法让一个已经发出去的码失效，除非：

- 它绑定了设备（`bind`），换机器就激活不了；
- 或者你换密钥（代价见第六节，所有用户一起遭殃）。

所以**退款不能靠「作废授权码」来实现**，只能靠别的手段。这是一个必须提前接受的现实。

### 9.2 退款流程

1. 确认退款条件成立（买断一般 7 天内无理由，订阅按已用时长折算，具体在售卖页面写清楚）。
2. **请用户主动解除授权**：设置 → 解除授权。这会删掉本机的授权码和设备指纹。
3. 在你的订单表里把状态标成「已退款」，并把对应的 note / 批次记下来。
4. 如果有绑定设备并且你愿意做得更绝，可以后续换密钥 —— 但这通常不值得，为一个 ¥18 的订单牺牲所有用户不值。

**诚实的话术建议：**

> 退款已受理。本应用的授权码是离线校验的，没有服务器可以远程吊销，所以需要你在 App 里点一下「设置 → 解除授权」把授权从设备上移除。这一步只能由你本人操作，抱歉。

### 9.3 换机

换手机是最常见的场景，比退款更常见。处理办法：

**没有绑定设备（`bind` 为空）的码**：直接让用户在新手机上重新输入同一个码即可。**什么都不用做。** 这是绝大多数订单的情况。

**绑定了设备的码**：用户在新手机上激活会提示「这个授权码绑定在另一台设备上」。此时有两个选择：

- **重新签一张不绑定的码**，让用户重新输入。同时更新订单表，注明「已换绑」。
- **让用户从旧手机上手动解除授权** —— 但这并不能释放 `bind` 字段（绑定信息在码里，不在本机），所以其实没用。

结论：**绑定只应该在有明确理由时使用**（比如高价值买断用户的防转售、或者明显的高风险订单）。默认不绑。

### 9.4 ⚠️ 换机流程里目前缺的一环

**App 目前没有把设备指纹显示给用户的入口。**

- 激活页内部确实算出了指纹（`UsageService.deviceFingerprint()`），但只用于验签比对，**没有展示给用户、也不能复制**。
- 这意味着：如果你签发了一个 `--bind` 的码，**用户没法把这个指纹告诉你**，你也就没法把码绑到他的设备上。

**这是一个真实的功能缺口，会直接卡住「绑设备」这个流程。**

修法很简单：在「设置」页或「解锁完整版」页加一个可复制的小字区块，显示 `deviceFingerprint()` 的值并说明用途（仅用于把授权码绑定到本机，不联网、不上传）。改动量大概十几行。

**在补上之前，不要签发绑设备的码。**

## 十、防止一个授权码被公开传播

授权码是离线字符串，**没有任何技术手段能阻止一个人把码贴到网上**。能做的是提高传播成本、让传播者得不偿失。

### 10.1 可选：绑定设备（最有效）

签发时带上 `--bind <设备指纹>`，这个码就只在一台机器上能用。传播出去别人也激活不了。

代价是换机麻烦（见 9.3），所以**只对高价值或高风险订单使用**。

### 10.2 批次号 + note 字段（追责用）

`note` 字段不参与验签，但它能让你在码泄露后定位到源头。

签发规范：

```
note 统一写成：<批次号>-<订单号或序号>
例：2026-11-A-0042
```

每一批（一个月或一批订单）用一个批次前缀。这样某个码出现在公开的地方，你可以：

1. 解码那个码，读出 `note`；
2. 查到是哪一单、哪个买家；
3. 联系处理。

**注意 `note` 是明文可见的**（payload 是 base64url，不是加密）。所以 `note` 里**不要写用户的姓名、手机号、邮箱** —— 那些等于公开信息。只写订单号和批次号。

### 10.3 其余手段（作用有限，但成本也低）

- **在交付话术里写明「授权码只在这台手机上生效，别转发给别人」。** 多数人不会特意去转发，但明示是有用的。
- **对同一订单不重复发货。** 一个订单只签一张码，重复的进线一律先核对订单表。
- **定期检查是否有异常激活。** 因为没有服务器，严格说做不到「统计活跃」；但你可以观察 GitHub Issues / 用户群里有没有人在求「免费授权码」。

### 10.4 什么情况下要动用换密钥

只有一个：**私钥泄露**（不是因为码泄露 —— 码泄露不泄露私钥）。

发现疑似泄露时的顺序：

1. 先确认，不要一上来就换密钥（换密钥代价很大，见第六节）。
2. 确认私钥确实泄露后：生成新密钥对、改 `publicKeyHex`、重新发布 App。
3. 通知所有已付费用户重新激活，给出补偿（比如延长订阅期）。
